# Sparkle Integration Plan

## What's done

- Sparkle 2.x added as SPM dependency (host app only)
- `SPUStandardUpdaterController` initialized at app launch
- "Check for Updates…" menu item under the app menu
- Placeholder `SUFeedURL` in Release build settings (`https://example.com/appcast.xml`)
- `release.sh` runs `generate_appcast` after building the notarized DMG
- Unit tests for the updater view model

## What's left

### 1. Generate EdDSA keypair

Run `generate_appcast` once to create the signing keypair. Sparkle stores the private key in Keychain automatically.

```bash
# After building the project, find the tool:
find ~/Library/Developer/Xcode/DerivedData -name "generate_appcast" -type f | head -1

# Run it on any directory — it will prompt to create a keypair on first run:
/path/to/generate_appcast /tmp/empty-dir
```

It prints the public key. Copy it for the next step.

### 2. Add `SUPublicEDKey` to Info.plist

Add the public key from step 1 to the host app's Release build settings in the xcodeproj:

```
INFOPLIST_KEY_SUPublicEDKey = <your-public-key-here>
```

This lets Sparkle verify that updates were signed by you.

### 3. Set the real `SUFeedURL`

Replace the placeholder `https://example.com/appcast.xml` in the Release build settings with the actual URL where you'll host the appcast. Options:

- **GitHub Pages**: host `appcast.xml` in a `gh-pages` branch or separate repo
- **GitHub Releases**: use a raw URL pointing to an `appcast.xml` asset attached to a release
- **Your own server**: any static file host works

### 4. Host the DMG and appcast

Each release needs two files uploaded to the server:

- `ConjureDSP-<version>.dmg` — the notarized installer
- `appcast.xml` — generated by `generate_appcast`, contains version info + EdDSA signatures + download URLs

The `enclosure url` in `appcast.xml` must point to where the DMG is downloadable. By default `generate_appcast` uses relative URLs, so the DMG and appcast should live at the same base URL, or you can manually edit the URLs.

### 5. Add release notes

Sparkle displays release notes to users in the update dialog. Two options:

- **HTML files**: create a `<version>.html` file per release in the appcast directory. `generate_appcast` picks these up automatically.
- **Inline in appcast**: add `<description>` elements to each `<item>` in `appcast.xml`.

### 6. Configure update checking behavior (optional)

Sparkle defaults are reasonable, but you can tune via Info.plist keys:

| Key | Default | Description |
|-----|---------|-------------|
| `SUScheduledCheckInterval` | 86400 (1 day) | Seconds between automatic checks |
| `SUAutomaticallyUpdate` | NO | Install updates without asking |
| `SUAllowsAutomaticUpdates` | YES | Show "Automatically install" checkbox |
| `SUEnableSystemProfiling` | NO | Send anonymous system info with update checks |

### 7. Test the full update flow

1. Build and archive version 1.0
2. Bump `MARKETING_VERSION` to 1.1, build a new DMG
3. Run `generate_appcast` on a directory containing the 1.1 DMG
4. Host the appcast and DMG locally (e.g., `python3 -m http.server 8000`)
5. Temporarily set `SUFeedURL` to `http://localhost:8000/appcast.xml`
6. Launch the 1.0 build — it should find and offer the 1.1 update

### 8. Automate appcast upload in release pipeline (optional)

Extend `release.sh` to upload the DMG and appcast to your hosting. For example with GitHub Releases:

```bash
gh release create "v${VERSION}" "$DMG_PATH" "$APPCAST_DIR/appcast.xml" \
    --title "v${VERSION}" --notes "Release notes here"
```
